How the data flows

Plaid→ Daily sync→ SQLite→ Litestream→ R2 backup
  • One service: a single FastAPI app renders server-side HTML with HTMX and installs as a PWA — no separate frontend, no SPA build.
  • Real bank data: Plaid in production; a daily job pulls balances and transactions via cursor-based sync.
  • Durable + cheap: SQLite on a volume, continuously replicated to Cloudflare R2 with Litestream. Restore is one command.
  • In-house logic: recurring-charge detection, net-worth history, and the bill calendar are computed from raw transactions, not bought.

The interesting part: a public demo that can't leak

This site is both my private tracker and a thing recruiters can click through. Those goals fight each other, so the demo is isolated by construction:

Request→ role?→ owner → real DB visitor → throwaway sandbox
  • Every anonymous visitor gets their own in-memory SQLite, seeded with realistic fake data, torn down when they leave.
  • A single routing guard picks the backing store from the session role — there is no code path where a demo request reaches my real tables, Plaid, or email.
  • Rate limits and an LRU cap keep anonymous traffic from exhausting the host.

Scoped on purpose

Lucre does four jobs well — balances & net worth, subscription detection, spending by category, and bills & alerts. I wrote down what I was not building (budgets/envelopes, investments, multi-user, bill negotiation) before starting, so the first version could actually ship.

The decision log and task board live in the repo: DESIGN.md, PRD.md, TASKS.md.
